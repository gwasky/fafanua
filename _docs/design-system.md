# Design System

Read this before changing anything visible on the site. It condenses Sections 4, 14 and 15 of `_docs/plan.md`, plus decisions made since; when the two disagree, raise it with the owner rather than guessing. For the Version 2 visual upgrade, `_docs/fafanua-v2-visual-upgrade-plan.md` governs layout, hierarchy, composition, motion and visual treatment, and overrides earlier visual rules where they conflict.

## Principles

- Restrained, credible, precise and modern, suitable for both private-sector executives and government decision-makers.
- Generous whitespace, clear hierarchy, subtle borders and a limited palette.
- No oversized heavy headings, loud gradients, glassmorphism, excessive animation, generic AI imagery, or stock photos used to fill space.

## Tokens

All design values live as CSS variables in `src/styles/tokens.css`: colours, type scale, font weights, spacing, border radii, container widths, shadows and motion durations.

- Never hard-code a hex value, font size or spacing value outside `tokens.css`. The lint step fails on hex colours elsewhere.
- Structure tokens so a dark theme could be added later, but do not build dark mode in this release.

## Typography

- Font: Inter, self-hosted with `@fontsource-variable/inter` (Latin subset), preloaded from `index.html`. No Google Fonts requests. It is loaded with `font-display: fallback`, not `swap` (#84): under `swap` with the preload, WebKit painted the homepage only once the font arrived, because text in a font that is still loading does not count towards its first paint. Under `fallback` the text shows in the metric-matched "Inter Fallback" after at most 100ms. A font that arrives more than about 3s after its request is not swapped in for that page view: the fallback stays, and the next page view uses the cached font.
- Fallback stack: `system-ui, -apple-system, "Segoe UI", Roboto, sans-serif`.
- Weights: 300 for large headings, 400 for body text, 500 only for small labels and buttons. Never bold headings. The capability titles (#83) are body-weight `h3`s, 400 at `--text-xl`. ## Logo

Files in `public/`: `fafanua-logo.svg` (positive), `fafanua-logo-reversed.svg`, `fafanua-logo-mono.svg` (uses `currentColor`), `fafanua-mark.svg`, `fafanua-mark-reversed.svg`, `favicon.svg` and `apple-touch-icon.png`. The source archive `_docs/logos.zip` is kept out of git; never commit it. The header uses the positive logo, and the reversed one while it is transparent over the hero; the dark footer (#60) uses `fafanua-logo-reversed.svg`, 160px wide.

The header logo is an inline SVG (#86), not an image, because of WebKit's first paint (#85): WebKit holds the first frame until the page is visually non-empty, text in a web font that is still loading does not count, and a logo image counted only once it had loaded, so with a slow logo file the homepage could stay blank until the font arrived (about 3.1s). A fixed-size inline `<svg>` counts as soon as it is laid out. The artwork still lives only in `public/fafanua-logo.svg`: at build time (and in dev) the `logoSymbol` plugin in `vite.config.ts` reads it and puts one hidden, `aria-hidden` `<svg>` (`display: none`, so it takes no box) at the start of every page's `<body>`, holding `<symbol id="fafanua-logo-art">` with the file's two paths, their `transform` and `d` byte for byte, and no fill or `<title>`; the build fails if the file is not that two-path logo. `Logo.tsx` renders `<svg role="img" aria-label="Fafanua Technologies" viewBox="0 0 5046 714" width="296" height="42" focusable="false">` with one `<use href="#fafanua-logo-art">`, the only inline SVG with `role="img"`. Its width is `min(10rem, 100cqi)` of the header row (`.site-header__inner` is an inline-size container) and its height that width times 42/296, the same box the image had at every width, including 320px with 200% text. The height must be a length, not `auto`: WebKit counted an SVG with `height: auto` as having no area. Each path is filled through an inline `style` from a token: the F symbol from `--color-logo-mark` and the wordmark from `--color-logo-wordmark` (teal 600 and graphite 900, the positive file's colours). `.on-dark` reassigns them to `--color-logo-mark-on-dark` and `--color-logo-wordmark-on-dark` (teal 400 and paper, the reversed file's), so the transparent header shows the reversed artwork with no script, in the pre-rendered markup too. The fills add no colour and no pairing. The footer stays a `<picture>` and `<img>`: it is below the fold and plays no part in the first paint.

Under a light forced-colours theme (`(forced-colors: active) and (prefers-color-scheme: light)`) the footer and the hero behind the transparent header are painted white, where the reversed logo's paper wordmark would vanish. For the header, one rule in `tokens.css` sets `--color-logo-mark-on-dark` and `--color-logo-wordmark-on-dark` to teal 600 and graphite 900 under that query, so the on-dark logo is the positive one there; the logo has `forced-color-adjust: none` (inherited into the `<use>` content), so a forced theme never repaints its fills, as it never repainted the image, and custom properties are never forced. The footer logo sits in a `<picture>` whose only `<source>` serves `fafanua-logo.svg` for the same query (#60); the `<picture>` is `display: contents`, so the image keeps its box, alt text and size. Normal colours and a dark forced theme keep the reversed logo there.

Under a dark forced-colours theme (`(forced-colors: active) and (prefers-color-scheme: dark)`) the solid header, light with normal colours, is painted black, where the positive logo's graphite 900 wordmark would vanish (1.28:1). A second rule in `tokens.css`, after the light one and mirroring it, sets `--color-logo-mark` and `--color-logo-wordmark` to teal 400 and paper under that query (#87), so the solid header shows the reversed logo on the forced black (paper 19.06:1, teal 400 9.57:1); `.on-dark` and `.surface-dark` already resolve to those colours, so the transparent header and the footer do not change. CSS cannot tell how light the forced `Canvas` is, and a system colour such as `CanvasText` would paint the logo outside its two variants, so both rules key off `prefers-color-scheme`, which in a forced-colours mode follows the forced theme's background; the footer's `<picture>` uses the same query, so header and footer always switch together. In a light forced theme and with normal colours the solid header keeps the positive logo. `e2e/forced-colours-logo.spec.ts` checks the painted wordmark's contrast in both forced themes and with normal colours: the transparent header, the solid header (the homepage scrolled, a service landing page, and the menu open at 360px) and the footer.

**Reveal safety rules** (`src/useReveal.ts`, #61):

- **One observer.** One `IntersectionObserver` for the whole page, created once in `useReveal()` (called by `App.tsx`), with thresholds 0 and 0.5. It unobserves each element once it has revealed, and is disconnected on unmount, which also shows anything still hidden. No scroll listener: the header's passive one stays the only one. No animation library and no dependency.
- **Opt-in markup.** A section is marked `data-reveal="section"`; the hook's `data-reveal="line"` mode, made for the lifecycle rail, is kept but unused since #83. Content is hidden only while the script has set `data-reveal-state="hidden"` on it, and the CSS that hides it (`components.css`) applies only under `@media screen and (prefers-reduced-motion: no-preference)`. So without JavaScript, without `IntersectionObserver`, under reduced motion (the script also does nothing then) and in print, everything is shown in its final state.
- **In view on load.** The observer's first report decides: an element already in view is never hidden and never animates, on a cold load and on a hash landing. One out of view is hidden, then revealed (`data-reveal-state="in"`, which transitions) the first time it comes into view, and never hides again. A reload or a history traversal hides nothing, because the browser restores the scroll position after the first report.
- **Hash landing.** Only a section's children move, never the section, which is the anchor target, so landing and `landOnHash.ts`'s guard measure an untransformed target. A later hash change (a typed hash) to an element inside a section that is hidden or still revealing, such as `#about-heading`, makes the script show that section in its final state and scroll to the target again (with the CSS `scroll-behavior`), so it lands clear of the header rather than `--reveal-shift` under it. A section's own id needs nothing, and cold loads are left to `landOnHash.ts`.
- **Focus.** When keyboard focus enters a section that is hidden or still revealing, the script drops its state during the focus event, so the section is shown at once at full opacity with no transform before the browser scrolls the focused element into view, and the focus ring is never under the header.
- **Tests.** `src/useReveal.test.tsx` (the observer mocked) and `e2e/motion.spec.ts` (Chromium and WebKit) check these rules; `e2e/fixtures.ts` has `waitForMotion` and `scrollThrough`, and `expectNoAxeViolations` waits for motion to end, so axe never measures partly faded text.
